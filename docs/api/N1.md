# N1 API reference and examples — NOA v2

N1 is the independent LINK object store. Present a LINK key; N1 calculates shard
placement and performs the object operation. Names, directories, history and
trash belong to [M1](M1.md) or an application's own metadata system. N1 does not
require M1 or its database.

Native **`n1://` / `n1s://` is the primary interface**, wire `n1/1`. HTTP is a
secondary adapter to the same handlers. The [NOA standard](../../NOA.md) defines
the contract; [link/src/noa.rs](../../link/src/noa.rs) defines the typed commands.

## Native Rust walkthrough

The workspace provides `N1NativeClient` in package `n1_native_client`.
[api_walkthrough.rs](../../native_client/examples/api_walkthrough.rs) is a complete,
executable example. It uses an existing configured N1 fragment, creates four
fresh objects and purges only those identities. It verifies multipart reconnect/
resume, repeated finalize, a full read, a signed range read, deep object health,
normal PUT, batch PUT, readback and 404 for a purged key.

```bash
export N1_URL=n1://127.0.0.1:19002
export N1_FRAGMENT=root
read -r -s -p 'N1 fragment secret: ' N1_SECRET; printf '\n'
export N1_SECRET
# Keep build output on your chosen build disk:
export CARGO_TARGET_DIR=/mnt/test-hdd-a/n1-build/target
cargo run --locked -p n1_native_client --example api_walkthrough
```

Expected terminal summary on success:

```json
{"verified_objects":4,"resumed":true,"repeated_finalize":true,"signed_range":true,"purged":4,"old_key_status":404}
```

The walkthrough needs read/write/delete permission, an available unsealed pool,
and a stripe between 8 bytes and 16 MiB to bound this demonstration's buffers.
It is a functional example, not a throughput benchmark or scale qualification.
Use `n1s://<certificate-name>:<port>` for verified TLS. The client trusts public
roots by default; `N1NativeClient::connect_with_tls` accepts a custom
`Arc<rustls::ClientConfig>` containing your private CA. It never disables
verification or falls back to plaintext.

The core API calls look like this; the complete file supplies the variables,
error handling, pool discovery and verification:

```rust
use n1_native_client::{Command, N1NativeClient};

// Inside an async function:
let mut client = N1NativeClient::connect(&url).await?;
client.auth_fragment(&fragment, &secret).await?;
let response = client.control(Command::UploadInit {
    pool: None,
    total_bytes,
    part_bytes,
    durable: true,
    ttl_seconds: 3600,
}).await?;
let key = response.result.as_ref().unwrap()["object_key"]
    .as_str().unwrap().to_owned();
client.write_at(key.clone(), offset, bytes, &mut source).await?;
client.control(Command::UploadFinalize { object_key: key.clone() }).await?;
client.download(key, 0, None, &mut destination).await?;
```

Each client owns an ordered connection. Use independent connections for
concurrent requests. Preserve the LINK key in your metadata before sending
payload. A cancelled/failed exchange makes that connection unusable; reconnect
and authenticate before retrying the **same** object identity.

## Native request and response framing

Every exchange uses four bytes of unsigned **big-endian control length**,
followed by a MessagePack map. Exactly `body_len` raw bytes follow that map.
The following JSON is the readable representation of a control map, **not** JSON
to send to a native socket. There is no JSON-string payload field in NOA v2.

```json
{
  "id":1,
  "command":{"op":"ping"},
  "body_len":0
}
```

Response, with N1's own package version, independent of M1 and the complete
system release (see [versioning](../VERSIONING.md)):

```json
{
  "id":1,"status":200,
  "result":{
    "engine":"Litiaina N1","version":"1.0.0-RC.2",
    "placement":"LINK-v1","noa":2,"native_protocol":"n1/1"
  },
  "error":null,"body_len":0
}
```

Request fields: `id` is a u64 echoed in the response; `command` is the tagged
`{op,args}` enum; `body_len` is a u64 defaulting to zero. Parameterless commands
omit `args`. Unknown fields are rejected. Unless marked optional in the table
below, an argument must be present; optional values can be omitted or null.
Responses always carry `id,status,result,error,body_len`. Ordinary successful
operations have status 200; native errors have non-200 status, a string error,
null result and no raw body. `maintenance.job` / `backup.job` can successfully
return null when there is no job.

Control is limited to 64 KiB before authentication and 8 MiB afterwards.
Parts/batches are at most 1 GiB per native request; normal PUT streams can be
larger within file-offset and plan limits. Bodies are never base64/JSON arrays
inside the control map. The transport has inactivity deadlines, not a fixed
maximum duration for an actively progressing large transfer.

## Authentication and pool discovery

Authenticate the connection with the configured fragment alias and its secret:

```json
{
  "id":2,"body_len":0,
  "command":{"op":"auth.fragment","args":{
    "fragment":"root","secret":"<N1-fragment-secret>",
    "permissions":{"read":true,"write":true,"delete":true,"repair":false},
    "ttl_seconds":3600
  }}
}
```

Result fields (inside the response envelope):

```json
{
  "token":"<access-token>",
  "session":{
    "session_id":"<session-id>","sub":"<32-hex-stable-fragment-id>",
    "permissions":{"read":true,"write":true,"delete":true,"repair":false},
    "operator":false,"exp":1794043600,"iat":1794040000,"iss":"<issuer>","aud":"<audience>"
  },
  "refresh_token":"<single-use-refresh-token>","refresh_expires_in":604800
}
```

IDs, lifetimes and timestamps are illustrative; retain server-issued values.
N1 uses **`token`**, whereas M1 login uses `access_token`. Permissions intersect
the configured fragment policy. `permissions:null` selects that policy; explicit
scoped permission requests do not grant operator authority. Maintenance/recovery
jobs need an operator-enabled configured fragment and an unscoped login allowed
by that configuration. M1's master key does not authenticate to N1.

`auth.bearer` with `{"token":"<token>"}` authenticates a new connection and
returns `{"session":<claims>}`. `session.info` returns current claims.
`session.refresh` with `{"refresh_token":"<current-refresh>"}` returns the
same login-result shape with rotated credentials. Save both new values;
reusing an old refresh token revokes its family. `auth.logout` clears the
connection and durably revokes its refresh session; an already-issued stateless
Bearer token otherwise remains valid until its expiry/current policy rejects it.

Discover immutable geometry before choosing part size:

```json
{"id":3,"command":{"op":"maintenance.pools"},"body_len":0}
```

Result shape, for an illustrative 1+1 pool:

```json
{"pools":[{
  "id":"<32-hex-pool-id>","generation":1,
  "data_shards":1,"parity_shards":1,"block_bytes":262144,
  "sealed":false,"available_members":2
}]}
```

`PoolId` fields serialize as 32 hexadecimal characters, not INI letters or ULIDs.
Use the discovered ID to select a pool, or `pool:null` for the last eligible
unsealed pool. Existing keys stay bound to their original immutable pool.
Discovery describes configured allocation geometry; cached live capacity and
member observations belong to `maintenance.health`.

## Upload lifecycle and response fields

This example uses the 1+1, 256 KiB-block pool above. Its stripe is
`data_shards × block_bytes = 262144` bytes. `part_bytes` must be a positive
multiple of the selected pool's stripe. Request a 524,295-byte object:

```json
{
  "id":4,"body_len":0,
  "command":{"op":"upload.init","args":{
    "pool":null,"total_bytes":524295,"part_bytes":262144,
    "durable":true,"ttl_seconds":3600
  }}
}
```

Successful result:

```json
{
  "object_key":"N1A1.<server-issued-key>",
  "total_bytes":524295,"part_bytes":262144,"parts":3,
  "expires_at":1794043600,"durable":true
}
```

`N1A1.<server-issued-key>` is a placeholder, not an encoded valid key. Never
invent a key for a write. Init generates a fresh identity and creates its
incomplete shard headers. It acknowledges allocation, not unused-key durability:
before the first durable payload, power loss may remove an unused allocation.
The first durable payload persists headers, bytes and staging ancestry.

Write part zero with this control, followed by exactly 262,144 raw bytes:

```json
{
  "id":5,"body_len":262144,
  "command":{"op":"upload.part","args":{
    "object_key":"<LINK_KEY>","offset":0
  }}
}
```

Result: `{"offset":0,"complete":true}`. Subsequent offsets are 262,144
(262,144 bytes) and 524,288 (seven bytes). The final short part does not need
stripe-sized user payload. N1 performs the EC padding internally.
An identical part retry is idempotent; different valid bytes conflict with 409.
Durable part ACKs require persistence on all members. Standard part ACKs do not.

After reconnecting with the retained key, request status:

```json
{
  "id":6,"body_len":0,
  "command":{"op":"upload.status","args":{
    "object_key":"<LINK_KEY>","start":0,"limit":4096
  }}
}
```

Result after only part zero:

```json
{
  "finalized":false,"finalized_shards":0,"parts":3,
  "checked_start":0,"checked_end":3,"missing_parts":[1,2],
  "unavailable_members":[]
}
```

`start` is a part index and `limit` is 1..4096; checked end is **exclusive**.
Advance with `checked_end` until all `parts` are covered. Status validates actual
parts and can perform I/O. An unavailable member is not a proof of a missing
part on that member. Retain progress in your metadata rather than continuously
scanning every object. Writes only open existing staging; an old key cannot
recreate an allocation removed by purge/GC.

After all parts are accepted:

```json
{"id":7,"command":{"op":"upload.finalize","args":{"object_key":"<LINK_KEY>"}},"body_len":0}
```

Result:

```json
{"object_key":"<LINK_KEY>","already_finalized":false,"total_bytes":524295}
```

The key stays identical. Repeated finalize validates finalized shards and returns
`already_finalized:true`. There is no extra object manifest or upload ticket.
Finalization does fixed work per pool member. Durable completed uploads carry
an ordered completion proof inside their shard footers. Normal uploads use
in-memory completion state; after that state is lost, query paginated
`upload.status` to reconcile all parts before retrying finalize. Missing
completion state returns `409` rather than scanning payloads during finalize.
The per-object finalization barrier is not a promise of atomic commit across
several objects or independent filesystems after a crash.

For normal upload, init with `part_bytes >= total_bytes` and stripe alignment,
then `upload.put` with exactly `total_bytes` raw bytes. PUT itself durably
publishes; a separate finalize is unnecessary. Its result has the finalized
object shape. For an empty object, choose a positive aligned part size and
`total_bytes:0`; the plan has zero parts, and PUT has a zero-byte body.

For batch, begin each single-part object separately, then send
`upload.batch {object_keys:[keyA,keyB]}` with bodies concatenated **in key order**.
The result is `{"objects":[<finalized-object>,...]}`. Limits are 256 identities,
1 GiB combined bytes and 1,024 calculated shard descriptors. Duplicate identities
are invalid. A batch is not an all-or-nothing transaction: after a lost/failing
reply, resolve each key independently. Successful PUT/batch/finalize always
durably publish, regardless of the plan's standard/durable part policy.

## Reads, integrity, health and purge

`object.stat` requires a key and returns this object-info shape:

```json
{
  "total_bytes":524295,"data_shards":1,"parity_shards":1,"finalized_shards":2,
  "integrity_algorithm":"LINK-SHA256-tree-v2","integrity_root":"<64-hex-tree-root>"
}
```

The integrity root is **not** SHA-256 of the complete raw file. New hybrid pools
use CRC32C frames and identity/position/length-bound source SHA-256; existing
SHA-256 pools report `LINK-SHA256-tree-v1`. GET verifies frames/reconstruction
before emitting requested bytes. Applications can additionally compare a
separately retained whole-file checksum.

Read eight bytes at offset 262,142 (across a stripe boundary):

```json
{
  "id":8,"command":{"op":"object.get","args":{
    "object_key":"<LINK_KEY>","offset":262142,"length":8
  }},"body_len":0
}
```

The response has `status:200`, `body_len:8`, object-info `result`, and exactly
eight following raw bytes. `length:null` reads to EOF. Native ranges are exact;
an out-of-object offset/length is rejected rather than silently truncated.
Do not request a streaming read through `client.control`; use `download`.

`object.signed_read` with `object_key,offset,length,ttl_seconds` returns:

```json
{
  "fragment":"<32-hex-fragment-id>","object_key":"<LINK_KEY>",
  "offset":262142,"length":8,"expires_at":1794040060,"signature":"<signature>"
}
```

Send that entire object as `object.get_signed {grant:<grant>}` or pass it to
`download_signed`. The receiving connection does not need login for this one
read. Grants last 1..21,600 seconds and never outlive the issuer's session token.
They bind all range/identity/expiry fields and grant no other operation. Current
fragment read policy and object existence still apply.

`object.health {object_key,deep:true}` returns `info` (object-info above),
`status`, `deep`, `verified_bytes`, and arrays `missing_shards,corrupt_shards,
unavailable_shards`. A healthy deep check has status `healthy` and empty arrays.
`deep:false` checks availability/structure without a complete payload scrub.
`object.repair {object_key}` returns `{"repaired_shards":[<indices>],
"total_bytes":524295}`; it requires repair permission and enough valid source
shards. Hardware replacement is an explicit operator workflow, not an API
permission to change enrolled geometry.

Explicit repair can also restore **completed but unpublished staging** when
enough shards retain valid completion seals and verified source stripes. It
writes reconstructed shards back under `.uploads/`; it does not finalize or
publish the object. Call `upload.finalize` separately after successful repair.
Incomplete staging or insufficient verified sources cannot be repaired this
way. Matching upload retries remain read-only once completion is recorded;
they cannot replace damaged completed or finalized data.

Purge:

```json
{"id":9,"command":{"op":"object.delete","args":{"object_key":"<LINK_KEY>"}},"body_len":0}
```

Result: `{"removed_shards":2}` in this complete 1+1 example; repeating purge
can return zero. Success removes incomplete/final shards and per-identity
staging directories, persists the removals, and leaves no identity record.
Old status/write/finalize/read requests return 404 and cannot recreate shards.
Only fresh init allocates a new random identity. There is no object listing,
rename, history or undelete in this API.

Keep a pending deletion key until success. A crash during purge has **not**
acknowledged deletion: surviving shards can remain readable if quorum exists.
Retry after restart/member recovery. M1 persists its own reclamation claim;
standalone clients must retain their own pending work. N1 keeps no permanent
per-object tombstone/retirement record.

## Complete command reference

Send each row as `{"id":N,"command":{"op":"...","args":{...}},"body_len":0}`
unless it has a raw body. Optional fields are marked `?`; all other fields are
required. Pool/fragment IDs are 32-hex strings; object keys are opaque strings.

| Operation | Arguments | Authority; result |
| --- | --- | --- |
| `ping` | No args | Public; product/version/placement/wire |
| `auth.fragment` | `fragment,secret,permissions?,ttl_seconds?` | Credentials; login result |
| `auth.bearer` | `token` | Token; `{session}` |
| `session.refresh` | `refresh_token` | Refresh credential; login result |
| `auth.logout` | No args | Authenticated; `{authenticated:false}` |
| `session.info` | No args | Authenticated; claims |
| `upload.init` | `pool?,total_bytes,part_bytes,durable,ttl_seconds` | Write; initialized plan |
| `upload.part` | `object_key,offset`; exact part raw body | Write; `{offset,complete:true}` |
| `upload.put` | `object_key`; exact total raw body | Write; finalized object |
| `upload.batch` | `object_keys`; concatenated raw bodies | Write; `{objects:[finalized objects]}` |
| `upload.status` | `object_key,start,limit` | Read or write; bounded status page |
| `upload.finalize` | `object_key` | Write; finalized object |
| `upload.cancel` | `object_key` | Write; `{removed_shards}`; unfinished staging only, not deletion of a published object |
| `object.stat` | `object_key` | Read; object info |
| `object.get` | `object_key,offset,length?` | Read; object info + raw response body |
| `object.signed_read` | `object_key,offset,length?,ttl_seconds` | Read; grant |
| `object.get_signed` | `grant` | Grant; object info + raw bytes |
| `object.health` | `object_key,deep` | Read; object health |
| `object.repair` | `object_key` | Repair; repaired indices/total bytes |
| `object.delete` | `object_key` | Delete; removed shard positions |
| `object.bulk_delete` | `object_keys` (1..256) | Delete; `{results:[{object_key,status,removed_shards? ,error?}]}`; inspect each row |
| `maintenance.health` | No args | Read; cached node/system/capacity/pools plus current counters/configuration |
| `maintenance.pools` | No args | Read or write; immutable pool profiles |
| `maintenance.gc` | No args | Operator; admitted staging-GC job |
| `maintenance.scrub` | `options:{repair,bytes_per_second,window_seconds}` | Operator; admitted scrub job |
| `maintenance.job` | No args | Operator; job or null |
| `maintenance.stop` | `job_id` | Operator; cooperative job state |
| `backup.list` | `repository,after,limit` | Operator; bounded array of recovery-point summaries |
| `backup.capture` | `repository,boundary_seconds` | Operator; admitted capture job |
| `backup.verify` | `repository,snapshot` | Operator; admitted verification job |
| `backup.replicate` | `repository,destination,snapshot` | Operator; admitted replication job |
| `backup.prune` | `repository,keep_last,protect` | Operator; admitted retention job |
| `backup.gc` | `repository,discard_incomplete` | Operator; admitted block-reclamation job |
| `backup.job` | No args | Operator; recovery job or null |
| `backup.stop` | `job_id` | Operator; cooperative recovery state |
| `backup.receive` | `repository` | Operator; switches connection to binary `LINK-replication-v1`; use `into_replication` |

Current LINK format permits total source length through `i64::MAX` and at most
16,777,216 internal parts; actual offset geometry and configured memory/part/I/O
admission can impose lower bounds. Init TTL is 1..2,592,000 seconds (30 days);
do not treat expiry as permission to GC a readable finalized object. Pool members
must be available for durable publication. Read availability follows the pool's
data/parity quorum and verified integrity.

## Maintenance and recovery examples

Do not poll by starting a new job each time. Start once, retain the job ID and
poll `maintenance.job` or `backup.job` with a bounded interval.

Scrub at 16 MiB/s in a one-hour window, checking without repair:

```json
{
  "id":10,"body_len":0,
  "command":{"op":"maintenance.scrub","args":{
    "options":{"repair":false,"bytes_per_second":16777216,"window_seconds":3600}
  }}
}
```

Scrub rate must be positive and at most 4 GiB/s; window is 1 second..7 days.
`repair:true` permits healing. `maintenance.gc` starts conservative expired
staging cleanup; M1 owns named trash TTL reclamation. A job has
`id,kind,phase,started_at,finished_at,report,error`. Poll:

```json
{"id":11,"command":{"op":"maintenance.job"},"body_len":0}
```

Phases are `running,stopping,completed,stopped,incomplete`. Stops retain admitted
I/O ownership until work drains. Reaching a window/resource bound makes a job
incomplete; it does not by itself declare N1 failed. Optional automatic schedules
are configured in the operator INI rather than created by health polling.

Recovery repositories are **operator-configured aliases**, never arbitrary
client paths/keys. Begin an online capture with a 30-second admission boundary:

```json
{"id":12,"command":{"op":"backup.capture","args":{"repository":"local","boundary_seconds":30}},"body_len":0}
```

Poll `backup.job` until terminal and inspect its result/error. The boundary
(1..300 seconds) controls capture coordination; the start response is not a
completed snapshot. Discover committed points using
`backup.list {repository:"local",after:"",limit:100}`; continue with the
last returned summary's `id` as `after`, stopping when the returned array is
empty. The result is an array, not a `{points,cursor}` envelope. A nonempty
cursor/snapshot/protected point is a canonical ULID. Verify and replicate a selected point:

Each summary contains `id,created_at,capture_mode,pools,members,files,records,
source_bytes,manifest_depth`. Recovery jobs have `id,kind,phase,started_at,
finished_at,result,error`; their operation-specific result appears only after
the work completes.

```json
{"id":13,"command":{"op":"backup.verify","args":{"repository":"local","snapshot":"<point-ULID>"}},"body_len":0}
```

```json
{"id":14,"command":{"op":"backup.replicate","args":{"repository":"local","destination":"replica","snapshot":"<point-ULID>"}},"body_len":0}
```

Wait for verification to finish before starting replication. One recovery job
runs at a time; overlaps return 409. Pruning requires `keep_last` 1..10,000 and
an explicit `protect` point, retaining at least one point. Repository GC protects
incomplete transfers unless `discard_incomplete:true` is explicitly chosen.
Cross-node transfer uses the authenticated `backup.receive` binary protocol and
the supplied recovery tooling; a raw recursive copy is not this backup API.
Restore is an offline operator operation documented in
[DOCUMENTATION.md](../../DOCUMENTATION.md#recovery-repositories), not an online
client command. N1 points do not include M1's database.

## Secondary HTTP examples

These examples use the same local port convention as the operator guide. HTTP
`POST /noa` accepts the exact JSON view of a native request and returns the NOA
response envelope. Binary upload bodies go to the dedicated streaming endpoints.

```bash
N1_HTTP=${N1_HTTP:-http://127.0.0.1:19001}
curl --fail-with-body --silent --show-error "$N1_HTTP/health"

login=$(jq -n --arg fragment "$N1_FRAGMENT" --arg secret "$N1_SECRET" \
  '{id:1,command:{op:"auth.fragment",args:{fragment:$fragment,secret:$secret,permissions:null,ttl_seconds:3600}},body_len:0}' |
  curl --fail-with-body --silent --show-error -H 'Content-Type: application/json' \
    --data-binary @- "$N1_HTTP/noa")
N1_TOKEN=$(jq -er '.result.token' <<<"$login")

n1_http() {
  curl --fail-with-body --silent --show-error \
    -H "Authorization: Bearer $N1_TOKEN" "$@"
}
n1_control() {
  n1_http -H 'Content-Type: application/json' --data "$1" "$N1_HTTP/noa"
}
profiles=$(n1_control '{"id":2,"command":{"op":"maintenance.pools"},"body_len":0}')
N1_POOL=$(jq -cer '[.result.pools[] | select(.sealed == false)] | last' <<<"$profiles")
N1_POOL_ID=$(jq -er '.id' <<<"$N1_POOL")
N1_PART_BYTES=$(jq -er '.data_shards * .block_bytes' <<<"$N1_POOL")

printf 'hello' > n1-hello.txt
initialized=$(n1_control "$(jq -n --arg pool "$N1_POOL_ID" --argjson part "$N1_PART_BYTES" \
  '{id:3,command:{op:"upload.init",args:{pool:$pool,total_bytes:5,part_bytes:$part,durable:true,ttl_seconds:3600}},body_len:0}')")
N1_KEY=$(jq -er '.result.object_key' <<<"$initialized")
n1_http -X PUT -H 'Content-Type: application/octet-stream' \
  --data-binary @n1-hello.txt "$N1_HTTP/noa/upload/$N1_KEY/bytes/0"
n1_control "$(jq -n --arg key "$N1_KEY" \
  '{id:4,command:{op:"upload.finalize",args:{object_key:$key}},body_len:0}')"
n1_http "$N1_HTTP/noa/object/$N1_KEY" --output n1-downloaded.txt
cmp n1-hello.txt n1-downloaded.txt
n1_http -H 'Range: bytes=1-3' "$N1_HTTP/noa/object/$N1_KEY" --output n1-range.txt
```

For this five-byte example, the selected stripe must be at least five bytes.
Successful HTTP part reply is `{"offset":0,"complete":true}`; control replies
have `result` inside the NOA envelope. Downloads return octet-stream with exact
Content-Length, Accept-Ranges, quoted integrity-root ETag and
`Cache-Control: private, no-store`. The Range request returns 206 with
`Content-Range: bytes 1-3/5`, body `ell`.

| Endpoint | Request / response |
| --- | --- |
| `GET /health` | Public version response, not an authenticated full health scan |
| `POST /noa` | JSON `Request`; body_len must be zero; JSON `Response`; control limit 64 KiB |
| `PUT /noa/upload/{key}/bytes/{offset}` | Exact Content-Length and raw part; JSON acknowledgement |
| `POST /noa/stream` | Exact total Content-Length; big-endian MessagePack control length + Request + raw PUT/part/batch body; JSON response |
| `GET /noa/object/{key}` | Bearer; optional offset/length query or one Range header; verified bytes |
| `HEAD /noa/object/{key}` | Bearer; metadata/ETag/preconditions without a payload download |
| `GET /noa/signed` | Grant query fields, no Bearer required; signed range bytes |
| `GET /noa/backup/receive/{repository}` | Operator Bearer; WebSocket upgrade for binary replication |

`/noa/stream` is not a JSON/base64 wrapper. Its Content-Length is
`4 + encoded_control_length + request.body_len`; the adapter limits the control
to 64 KiB and validates the body against the existing plan. Use the native Rust
client for ordinary large-file transfers rather than building the complete
stream in memory to determine its length.

HTTP GET/HEAD support If-None-Match (304), If-Match (412), a single Range (206 or
416), and exact strong-ETag If-Range. Range ends/suffixes past EOF are clamped;
native/query offset+length ranges remain exact. An If-Range mismatch yields a
full response. Do not combine an explicit query/signed range with a Range header.

Example signed URL from the whole `object.signed_read` result:

```bash
grant=$(n1_control "$(jq -n --arg key "$N1_KEY" \
  '{id:5,command:{op:"object.signed_read",args:{object_key:$key,offset:1,length:3,ttl_seconds:60}},body_len:0}')")
curl --fail-with-body --silent --show-error --get \
  --data-urlencode "fragment=$(jq -er '.result.fragment' <<<"$grant")" \
  --data-urlencode "object_key=$(jq -er '.result.object_key' <<<"$grant")" \
  --data-urlencode 'offset=1' --data-urlencode 'length=3' \
  --data-urlencode "expires_at=$(jq -er '.result.expires_at' <<<"$grant")" \
  --data-urlencode "signature=$(jq -er '.result.signature' <<<"$grant")" \
  "$N1_HTTP/noa/signed" --output n1-signed-range.txt

# Physically purge only the fresh key created in this walkthrough:
n1_control "$(jq -n --arg key "$N1_KEY" \
  '{id:6,command:{op:"object.delete",args:{object_key:$key}},body_len:0}')"
```

## Errors and retries

Native/control errors use the same response fields as success:

```json
{"id":15,"status":404,"result":null,"error":"not found","body_len":0}
```

The error text is illustrative; branch on status, not on English wording.
HTTP control uses that envelope; errors in raw HTTP endpoints/extractors can
instead be `{"error":"<reason>"}` or framework text. `N1NativeClient` returns
`NativeClientError::Native {code,message}` for service errors; `code` is the
status as a string. Transport/protocol errors are separate variants.

| Status | Meaning / action |
| --- | --- |
| 400 | Invalid key encoding, arguments, geometry, range or body shape; fix request |
| 401 | Missing/invalid/expired authentication; log in or rotate credentials |
| 403 | Permission/operator/scope denial; do not retry unchanged |
| 404 | Absent upload/object; continuation cannot recreate it |
| 409 | Conflicting immutable bytes, expired staging or active-job conflict; inspect lifecycle/job |
| 413 | Transport/body/control admission limit |
| 422 | Verified shard/format/integrity failure |
| 429 | Peer/fragment request quota; back off with jitter |
| 503 | Unavailable quorum/member, incomplete purge or exhausted admission; no success guarantee |
| 507 | ENOSPC or filesystem quota exhaustion |

Prefer bounded backoff and status/retry by the retained key. Identical writes and
repeated finalize are idempotent; a fresh init creates a **different object**.
After a partially transmitted exchange reconnect before any command. Never
interpret a final filename or successful response headers as proof that a failed
payload transfer or interrupted purge completed. Keep pending deletion intent
in the client/metadata until durable success.
