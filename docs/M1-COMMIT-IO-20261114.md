# M1 database append I/O — November 14, 2026

The bounded M1 append optimization passes regression, process-crash, disk-full
and service checks with N1 fixed. Small-object tail acceptance and the RC.2
release gates remain open.

This stage holds N1 at the tested `staged02` executable and changes only M1's
database appender. Previously, every value, tree node and commit record issued
its own positioned write. The candidate combines consecutive small records
within one commit in a buffer bounded at 64 KiB. This reduces filesystem calls
without adding a batching delay or removing a durability barrier.

## Ordering and bounds

Record encoding, checksums, offsets, 4 KiB commit boundaries, snapshots and
conflict validation are unchanged. The writer drains its buffer before returning
a completed commit. The existing successful file `sync_all` still precedes
root publication and successful replies. M1 still durably reserves the pending
identity before forwarding payload, then durably publishes the name after N1
confirms completion. N1's payload, direct-I/O, io_uring, repair, purge and
publication paths are unchanged.

An oversized record uses the previous exact positioned-write path after
draining any preceding buffered records. Append errors still prevent publication
and poison further writes. A checkpoint uses the same bounded appender and
drains each completed commit before replay can reference its new root. Its
existing generation/manifest synchronization is retained. There is no new
format, dependency, INI option, background queue or permanent object record.
The added buffer belongs to an appender, not to every queued transaction or
object in the catalogue; existing large-record and cache budgets still apply.

## Small-object comparison

The order is **candidate–baseline–baseline–candidate**. Each phase runs five
repeats of 100 strict 4 KiB uploads at concurrency one, 100 at concurrency eight
and one separate one-shot control: **1,005 objects per phase, 4,020 total**.
Every payload passes complete length/SHA-256/version readback. Scoped GC,
offline database verification and marker-only N1 file censuses pass afterward.

Each cell below pools 1,000 original samples from the two phases for that
binary and concurrency. Quantiles use nearest rank; phase p99s are not averaged.
Wall time sums upload windows, excluding readback and cleanup.

| Observation | Baseline | Candidate |
| --- | ---: | ---: |
| c1 upload-window seconds | 11.412 | 10.280 |
| c1 p50 / p95 / p99 ms | 9.200 / 16.397 / 94.352 | 9.361 / 16.680 / 24.911 |
| c8 upload-window seconds | 4.712 | 3.708 |
| c8 p50 / p95 / p99 ms | 20.575 / 40.524 / 405.669 | 20.365 / 40.417 / 338.954 |
| M1 upload CPU seconds, both modes | 3.23 | 3.11 |
| N1 upload CPU seconds, both modes | 4.69 | 4.62 |
| Highest sampled M1 upload RSS KiB, both modes | 57,748 | 58,024 |

Candidate total time is shorter in this window, while its c1 median/p95 and
RSS are slightly worse. CPU is a process-tick observation under variable
desktop load, not a frequency-controlled efficiency claim. The long tails
remain: the individual c8 phase p99s are **44.783 and 388.766 ms** for the
candidate, versus **982.628 and 42.462 ms** for the baseline. Candidate maximum
latency reaches **534.300 ms**; baseline reaches **985.141 ms**. A faster pooled
result does not establish that the stalls are fixed.

Two separate instrumented 1,005-object controls count M1 syscalls across the
complete workload, including verification and cleanup:

| M1 syscall | Baseline calls | Candidate calls |
| --- | ---: | ---: |
| `pwrite64` | 131,155 | 9,927 |
| `fsync` | 7,424 | 7,448 |

This records **92.4% fewer positioned-write calls**. Compatible transaction
grouping and filesystem state can vary between runs; the synchronization policy
is unchanged. These counts are not physical write-byte reductions or disk IOPS.
Tracing changes timing, so these phases are excluded from the untraced latency
comparison. Both instrumented controls pass the same integrity/cleanup checks.

## Large-file controls

staging. Each object is read back completely, finalized again and reclaimed.
The initial A–B pair is followed by B–A because its first candidate upload is
3.1% slower. The separate 1 GiB controls run between those two pairs; these are
four individual observations, not four uninterrupted saturation phases.
All original samples remain separate; CPU observations from the

## Completed service checks

The candidate passes the 19 storage regression cases, including append/sync
errors, byte-by-byte suffix recovery, corruption rejection, concurrent snapshots
and online checkpoints. Its test-only crash helper remains explicitly ignored
as a standalone case and is invoked by the parent fault test.

Eight real-service cases pass on the two distinct HDD filesystems with N1
`staged02`: original public/native contracts, member loss/corruption, complete
metadata restore, the in-flight process-crash matrix, lost unused allocation,
bridge integrity/restart, both-process interruption and staged-object repair.
These are private directory/member faults, not a physical host power cut.

Four original Console workflows pass against the candidate in a fresh private
test fragment: flat-prefix rename/TAR, re-added multipart resume, small batch
and reload/resume without resending acknowledged parts. Console product and
test sources are unchanged. The first reused-fragment run passes three cases
but fails the flat-prefix first-page locator: previous runs have filled the
200-item first page. The unchanged baseline reproduces the same failure.
The crowded fragment and both failed traces are retained; the corrected fresh
fixture changes no product behavior or test assertion.

The baseline M1 checker also verifies four stopped candidate databases, and
the candidate checker verifies a stopped baseline database. These complete
tree/value checks retain the same on-disk format rather than relying solely
on the candidate validating its own output.

The storage parent fault test is extended with a ninth kill/reopen iteration.
It appends eight 32 KiB values, pauses before the commit record, verifies that
more than 64 KiB has left the userspace buffer for the file, then kills the
child. Recovery must expose exactly the three previously acknowledged records
and no partial new transaction. This passes on DATA_SSD and the workstation HDD.
The helper is entirely test-only;
rebuilding the normal M1 binary still yields the exact measured executable.

A separate real ENOSPC test passes on a private **512 MiB XFS loop filesystem**
backed by DATA_SSD. Only M1 uses the constrained filesystem; N1 shards and the
independent ACK oracle remain on healthy storage. The original test fills that
private filesystem, requires a bounded failure rather than a timeout, reopens
after freeing space, verifies acknowledged data and accepts a new write.
The private mount is unmounted and its exact loop device detached afterward.
The host filesystem is never filled. This is one existing service case, not a
new distinct test or a physical device failure simulation.

The complete release workspace passes **426 tests, zero failed**, with
74 explicit existing helper/opt-in exclusions. The strengthened parent fault
case is additionally rerun on SSD and HDD; it is not counted as nine new tests.
Strict release workspace/all-target Clippy, strict storage all-target Clippy
and formatting pass. The default workspace uses the workstation HDD for its
temporary fixtures and external build target; its byte-by-byte recovery sweep
finishes without skipping cuts.

All **380 Rust/Cargo files** match the SSD test system source manifest,
including the test-only extension. N1/LINK/native-client runtime preservation

`source/m1-append32-bench.sh`, `m1-append32-traced.sh`, `m1-append32-hdd.sh`,

No million-object campaign, release or tag is created in this stage.

## Scope

The selected optimization reduces M1 append-call overhead. Its file bytes and
required synchronization policy remain the same. The shared-filesystem waits
identified in the latency investigation remain possible with frozen N1; a
smaller syscall count does not eliminate XFS/device flush latency.

The original million-object evidence is preserved without restarting it.
Physical power-loss, the four-HDD reference system and remaining
saturation/operator/performance gates remain tracked in [the RC.2
checklist](RC2-IMPLEMENTATION.md).
