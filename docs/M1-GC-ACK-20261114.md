# M1 multipart acknowledgement and GC ordering — November 14, 2026

M1's durable multipart ACK records now serialize with cancellation, publication,
trash and GC claims in one metadata transaction. Indexed GC defers active upload work
without waiting behind a slow client. This is M1 hardening: N1's key lifecycle,
placement, file format and standalone object API are unchanged by these M1
changes.

## Ordering

An aligned durable part first receives its normal N1 acknowledgement. Before M1
records the durable progress bit, its transaction rechecks the saved plan, pending
upload, logical owner and upload-GC claim. A bridged part uses the same fence
when recording its staged-file receipt. A claim/trash mutation which wins after
an ACK transaction has read those keys conflicts with its commit; its retry
refuses the ACK. Relaxed native parts retain their existing policy without a
new per-part database receipt. Detached database workers cannot bypass this check
merely because their HTTP future was cancelled.

The physical slow-client witness reproduces the old failure on two HDDs:
metadata GC waits behind a native upload whose HTTP body has not finished. The
corrected executable completes a deferred pass, refuses the late part ACK after
the owner is trashed, then reclaims the version once its writer exits. The same
test covers both native-aligned and bridged parts, verifies the unrelated live
object after killing/restarting both engines, and checks the offline database.
The old failure and corrected pass use the same Rust harness and N1 executable.

The existing per-upload lock map is shared with M1 maintenance. Foreground
operations keep their existing locks. GC tries exclusive ownership for the
specific version before physical purge and metadata cleanup; an active writer
increments the deferred count and leaves its existing due/claim index intact.
GC does not wait on an unrelated request, add a global upload lock or scan the
namespace or N1's final shard directories. Once the writer exits, a later pass
can reclaim that version normally. Transaction fences still protect work
already owned by an asynchronous database worker after its request exits.

## Durable staging directories

A synchronized part file is insufficient if a crash loses the new directory
entries which lead to it. M1 establishes its configured staging-root ancestor
chain once before listening. The first strict bridged receipt for a version
also synchronizes its version, fragment and staging-root directories before
the database receipt commits. A private plan flag records that successful
boundary. Subsequent parts retain the existing version-directory barrier;
concurrent first parts may repeat the initial parent barriers. Normal/strict
policy and payload SHA-256 checks are preserved. No request calls `syncfs` or
walks an ancestor chain.

Actual `ENOSPC` and quota exhaustion in M1 staging/storage return 507 with a
generic capacity message, without exposing private paths. Other I/O failures
retain their existing error policy. Clients must retain the same upload
identity, restore capacity, query ACKs and resend only missing identical parts.

## Qualification boundaries

The storage-full fixtures use private 512 MiB loopback XFS filesystems on
DATA_SSD, with the ACK oracle, metadata control and object payloads outside the
pressured staging filesystem. Only those new loop devices are formatted; no
physical DATA_SSD/HDD device is reformatted or filled.

The first staging-pressure attempt reached ENOSPC for a 1 MiB filler write but
left room for the smaller part, which correctly succeeded. That fixture failed
its intended precondition. The corrected Rust filler consumes the remaining
4 KiB allocation units too. The failed log is preserved alongside the corrected
run; a successful ACK while space remains is not classified as data loss.

All workload, fault and verification logic is Rust. Process termination and
file/directory synchronization checks do not reproduce a physical power cut.
The remaining RC.2 release conditions still apply.

## Matched performance

The main-PC DATA_SSD 1+0 comparison holds N1 staged02 fixed and alternates M1
negotiate02 / gc-ack04 in ABBA order, reversing case order between phases.
Both paths use identical explicit external geometry, four strict durable
writers and the same benchmark executable. Every source is completely read
back with SHA-256/version/length checks, finalized twice, reclaimed through
indexed GC and followed by an offline database check and marker-only pool
census. No builds, functional campaigns or other qualification workload run
concurrently with a timed comparison. Desktop activity remains recorded.

The first bridged baseline is substantially faster than its second sample.
This does not erase the **8.63% aligned and 26.92% bridged aggregate throughput

neither a speedup nor complete performance parity. Native-aligned geometry
still avoids bridged finalization's payload copy; that existing limitation
remains separately documented.

A separate ABBA measures **400 strict 4 KiB single-part multipart objects**,

benchmark permits up to 512 repeats only for small-object-only workloads at
most 64 KiB each; larger/mixed workloads retain the five-repeat guard. Its
three regression tests and scoped strict Clippy pass. Both M1 binaries use
the identical new client, SHA-256

The first attempt was refused by the old repeat guard before creating a

omitting directory persistence. Further optimization must preserve the
transaction fence and these acknowledgement guarantees.
