# M1 bridge I/O and backing-allocation recovery — November 14, 2026

M1 now verifies and forwards staged multipart files together, reducing repeated
physical reads of large sources. Its durable source remains the recovery copy
until N1 confirms durable completion and M1 publishes the named version. N1's
LINK, checksums, aligned O_DIRECT writer, io_uring driver and runtime source
remain fixed throughout this qualification.

## Changes and guarantees

Previously, bridge finalization checksum-read the entire source before reading
it again to convert its geometry. Each small verification buffer also incurred
Tokio filesystem scheduling and copying. The selected implementation verifies
one whole external file in one owned blocking worker, rewinds that descriptor,
and forwards it before opening the next file. A corrupt file is rejected with
422 before any of its bytes reach N1. Earlier valid native parts may exist;
immutable retry verification still applies when conversion is retried.

The memory reservation outlives a cancelled caller while its verifier is still
running. Memory and open-file counts remain bounded independently of object
length. Converted native parts use normal mode because strict external ACKs
already have synchronized M1 source files, directory links and database
receipts. N1's final durability/publication barrier is unchanged. Direct native
durable ACKs, existing saved upload plans and public client geometry are not
weakened or silently rewritten.

An interrupted conversion replays M1's retained source. A separate fault witness
exposed another case: an unused N1 Begin may legally be lost before its first
durable payload. M1 now probes its allocation with an empty native status range,
reading headers without a payload walk. Only a confirmed 404 for total absence
permits a fresh Begin in the same pool/generation. Its pending private key,
reference and expiry index switch in one M1 transaction. The public session,
version, logical path and source ACKs remain unchanged. The old LINK remains
404. Cancellation, publication, trash and reclamation fence the replacement;
an unavailable, corrupt or partly missing allocation is not reset this way.

This does not restore missing published objects or assert physical power-loss
qualification. The allocation-loss fixture explicitly removes only unused
128-byte headers after stopping its private engines.

## Linux I/O choices

Every selected physical service and benchmark invocation explicitly requests
`N1_IO_BACKEND=uring`; that setting fails initialization rather than silently
falling back. N1 retains direct I/O for aligned interior payload pages and
buffered handling for isolated unaligned boundaries. Small files retain their
existing path. No N1 runtime code changes in this stage.

M1's small database records retain positioned buffered writes and group fsync.
Its staged source benefits from verifying and forwarding the same file while
that part is cached. This stage adds no ring dependency, direct-I/O padding,
database format, INI option, permanent object record or background queue.
The measured large-file cost is redundant payload I/O, not a reason to redesign
the specialized database again.

## Large-file observations

The fixed Rust client generates bounded deterministic data, uses loopback HTTPS
to M1 and native TLS to N1, uploads with four writers, verifies every complete
readback by length/SHA-256/version, repeats finalize and performs scoped GC.
Each phase then checks M1 offline and requires N1's member census to contain
only its pool marker. M1 staging, database and N1 shards share DATA_SSD here.
No host page-cache drop or cold-read claim is made.

Processes are pinned to P-core logical CPUs 0–11. The main PC normally uses
powersave, and frequency variation substantially affects CPU seconds. Matched
performance windows temporarily select performance on only those policies,
retain their original governor/energy preferences, and automatically restore
them on exit or a bounded timeout. Original settings are verified afterward.
Profiling is separate from the timed comparisons.

The final `bridge24` comparison runs candidate first, baseline second, one
15 GiB object each, explicit 8.125 MiB external parts and 1,891 parts per object.
The earlier exploratory `bridge23` pair runs in the opposite order and is
retained separately, not pooled as though it were the same executable.

## Small-object controls and remaining tails

The initial matched small control runs three repeats of 100 × 4 KiB objects
at concurrency 1 and 8 per binary, plus three one-shot controls: 603 verified
and reclaimed objects per side. It records slower candidate concurrency-1
total time (4.099 versus 2.900 seconds), faster concurrency-8 total time
(2.996 versus 3.675 seconds), and worse concurrency-8 p99 (825.631 versus
470.849 ms). It does not support a small-object latency improvement claim.

A separate B-A-A-B follow-up after the large runs uses the restored normal
powersave CPU policy, the same binaries/configuration, three repeats per phase
and full verification/GC/offline/census checks. No CPU-policy change or other
test/build workload runs during it. It contributes 1,206 objects per side,
including 600 per concurrency and six one-shot controls. The fixed one-shot
path does not use the changed multipart bridge. CPU seconds are strongly
frequency-dependent; do not pool this window with the performance-policy runs.

Candidate concurrency-8 p99 remains worse despite the shorter total time and
lower median/p95. Both unchanged baseline and candidate have intermittent
long stalls; their cause is not established by these observations. Original
samples are preserved in `bridge25-small-*` and `bridge25-small-control-*`.
Small-object tail acceptance remains open; a large-upload win does not close
it. This report neither removes the adverse samples nor declares parity.

The subsequent [latency investigation](M1-LATENCY-20261114.md) reproduces the
small-object stalls with correlated request/syscall timing and XFS kernel
stacks. It identifies durable commit and publication waits, including N1's
filesystem-wide `syncfs` dependency when M1 shares that filesystem. Its RAM
isolation control is diagnostic and does not close persistent performance
acceptance or retroactively trace these original samples.

## Rejected work and release scope

Concurrent conversion (`bridge21`) passes its integrity tests but regresses
throughput/CPU and is removed. Deferring the converted-copy part flush alone
(`bridge22`) does not establish a throughput win. Source overlays, original
measurements and errors remain in the private evidence. A separate combined
upload/GET CPU profile finds SHA-256, TLS, copying and filesystem work prominent;
its percentages are not upload-only or M1-only attribution.

The previous million-object campaigns are preserved rather than restarted.
This local stage does not requalify those counts for its new binary. Physical
host power loss, final four-HDD MCH qualification, sustained saturation and
complete contract/operator/performance acceptance still govern RC.2. No tag
or release is created.
