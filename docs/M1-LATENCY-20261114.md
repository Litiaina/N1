# M1/N1 upload latency investigation — November 14, 2026

The reproduced small-object stalls are predominantly in durable M1 commits and
N1 PUT, with a demonstrated shared-filesystem dependency. N1's publication
barrier uses `syncfs`, which covers the filesystem containing its shards. In
this test, that filesystem also contains M1's database. Correlated syscall
timings and kernel stacks show both services waiting for XFS log persistence.
This investigation identifies a cost; it does not claim to fix it or close
performance acceptance.

The large-file bridge has a separate cost: explicit incompatible part geometry
requires M1 to forward retained source bytes during finalize. The
[bridge I/O report](M1-BRIDGE-IO-20261114.md) measures that path and the negotiated
direct path separately. The small one-shot requests below do not use that bridge.

## Where one-shot upload waits

The strict named one-shot path performs these ordered steps:

1. Authorize, acquire an upload slot and obtain a fresh N1 allocation.
2. Commit M1's pending identity/reference before forwarding payload.
3. N1 writes and seals shards, persists the files, publishes them and waits for
   its filesystem publication barrier.
4. Read the finalized N1 stat and commit M1's named publication before success.

There are two M1 commit barriers and N1's file/publication barriers on this path.
M1 already supports group commit, and N1 already joins pending `syncfs` callers
on the same filesystem. Neither mechanism makes storage synchronization free.
The relevant implementation is `metadata_engine/src/service.rs`,
`metadata_engine/storage/src/worker/group.rs`,
`object_engine/src/core/upload/small_batch.rs` and
`object_engine/src/core/linux_io/group.rs`.

In `latency27-ssd-a2`, client request 102 takes **842.008 ms**, with **838.273 ms**
inside the server handler:

The reservation includes 348.354 ms inside the commit call. There are **zero

Across the captured slow runs, worker admission, connection admission, TLS

hundreds of milliseconds. A separate 637.183 ms server request is a single
one-shot control, not a concurrency-eight sample; its reservation, native PUT

## Correlated syscall and kernel proof

Selective `strace` in `latency26-profile-p6-traced` records request 82 starting
at Unix microseconds `1794652690542720`, taking 205.661 ms in the server.
Its N1 PUT takes 119.751 ms and M1 publication takes 82.723 ms. The corresponding
syscalls are:

```text
1794652690.548864  N1 syncfs(member0)          115.924 ms
1794652690.666082  M1 fsync(database store)     82.126 ms
```

Their timestamps fall inside those stages of that same request. The database
checkpoint `CURRENT` rename in this trace occurs about 16 seconds later, so it
does not explain this request. Whole-process maxima from startup or cleanup
are not substituted for request timings.

A separate bounded, read-only root `/proc` sampler in `latency27-kernel-p7`
captures these call chains:

```text
M1 m1-commit:    fsync -> xfs_file_fsync -> xfs_log_force_seq -> xlog_wait_on_iclog
N1 iou-wrk:     io_fsync -> xfs_file_fsync -> xfs_log_force_seq -> xlog_wait_on_iclog
N1 n1-runtime:  syncfs -> xfs_fs_sync_fs -> xlog_wait_on_iclog
```

This establishes that N1's io_uring fsync is active and can wait on XFS log
persistence just as M1's commit does. Direct payload I/O does not eliminate
filesystem log ordering. Linux documents the filesystem-wide scope of
[`syncfs`](https://man7.org/linux/man-pages/man2/sync.2.html); XFS documents why
[synchronous log forces wait for stable storage](https://docs.kernel.org/filesystems/xfs/xfs-delayed-logging-design.html).

The kernel/strace run passes verification but is diagnostic: instrumentation
changes timing. It is excluded from the untraced comparison below. Stack sample
counts are not CPU seconds or exact wait durations. These captures do not
retroactively trace the original report's 1,129.739 ms p99 sample.

## Isolation control: change only M1's database medium

Two identical stopped copies of the private M1 database are made before the
experiment. A uses a private DATA_SSD directory; B uses `/dev/shm`. Only M1's
`data_dir` changes. N1 remains on the same physical DATA_SSD, with the same
binary, pool and configuration. The order is **A–B–B–A**. Each phase runs five
repeats: 500 strict 4 KiB one-shots at concurrency one, 500 at concurrency eight,
and five separate single-object controls.

Every phase verifies complete payload length/SHA-256/version, reclaims its
objects through scoped GC, checks M1 offline and requires a marker-only N1
member census. Each phase has 1,005 server profiles, 1,000 uniquely matched
small-benchmark client IDs, no unmatched/duplicate IDs and **zero dropped events**.
The extra five server profiles belong to the separate one-shot controls.

RAM files consume memory outside process RSS: the final RAM database is about
190.6 MiB. These RSS measurements cannot be presented as total host memory
cost. CPU deltas use process ticks and are coarse for short windows.

Removing M1's physical persistence traffic removes the reproduced long tails in
both RAM phases; returning it restores them. Together with correlated syscall
timings and kernel stacks, this identifies persistence and shared-filesystem
coupling as the main observed latency mechanism. It does not independently
separate XFS ordering, SSD/controller flush latency, device queue state and
desktop scheduling. It does not establish that the SSD is faulty or that the
game causes the stalls. The RAM control is **not a durable deployment or an
RC.2 performance pass**.

## Instrumentation and verification

The opt-in Cargo feature `upload-profile` adds bounded, per-request timings for
HTTP one-shot uploads. It propagates context into the existing metadata worker,
records commit/conflict counts and emits a numeric `x-m1-upload-profile`
response header to join Rust client samples. Events are limited to 128 per
request; names, paths, LINK keys, tokens and credentials are not logged.
Parent and nested stage timings overlap intentionally. Cancelled requests need
not produce a completed record; complete counts are checked for these runs.

Normal builds exclude the profiling module, middleware, task-local context,
timers, events and response header. The disabled timing macro expands to the
original future. This is investigation tooling, not a new NOA contract or an
always-on production monitor.

```sh
cargo build --release -p m1 --features upload-profile --bin litiaina-m1 --locked
cargo build --release -p m1 --example throughput_bench --locked
```

The current source passes **426 default release workspace tests, zero failed**,
with 74 explicit existing helper/opt-in exclusions. Strict release workspace
Clippy and feature-enabled M1 all-target Clippy pass. Formatting and N1 source
preservation are checked separately. The real-service phases above exercise
profile propagation, client correlation and the event limit without dropped
events. No payload, persistence, publication or GC behavior is changed here.

Raw evidence includes `profile.jsonl`, `CORRELATED.json`, per-request client
samples, syscall traces, kernel stacks, host load, artifact hashes, offline
checks and physical censuses. The drivers and jq reduction are under `source/`.
The initial macro/module naming collision is a retained compile failure,
corrected before measurement. An exploratory 12-repeat invocation is rejected
by the existing 1–5 repeat harness guard before payload work; its failure is a
setup error, not an engine or integrity result. Completed phases remain distinct
from those failed attempts.

## Optimization boundary

The next selected optimization holds N1 fixed and reduces M1's database append
calls; see the [M1 commit I/O follow-up](M1-COMMIT-IO-20261114.md). It retains both
M1 durable transaction boundaries and N1's existing publication barrier.

N1's current filesystem-wide barrier still couples unrelated writers on the
same filesystem; M1's two durable transaction boundaries also contribute.
A narrower publication barrier would have to persist every changed directory
and newly created ancestor, retain data-before-publication ordering, pinned
member/error checks and crash/retry guarantees. Simply deleting `syncfs`,
acknowledging M1 commits before fsync, or putting a production database in RAM
does not meet that requirement.

A persistent separate-media/filesystem control is still needed before claiming
production tail recovery. This stage deliberately holds N1 fixed to identify the
cost and does not silently change its tested persistence path. Large bridge
conversion and small-object synchronization remain separate optimization work.
Final hardware power-loss, the four-HDD reference system, saturation and
complete operator/contract acceptance conditions remain in [the RC.2
checklist](RC2-IMPLEMENTATION.md).
